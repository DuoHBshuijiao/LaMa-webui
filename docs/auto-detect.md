# 自动定位水印并划分遮罩区块 · 技术选型

> 目标：把现在的"上传 → 手工涂抹 → 修复"变成"上传 → 自动出候选区块 → 一键确认/微调 → 修复"。
> 约束：本机离线、Windows、Python 3.11、单卡 8 GB、前端零构建、MIT 许可、LaMa 单帧 1–3.5 s。
> 实测环境：AMD Ryzen 7 3700X（8C/16T）、ONNX Runtime 1.32.0 CPU、Python 3.11.7、`samples/demo-watermarked.jpg`（1600×1067，双水印）。

## 0. 结论

1. **单模型无解，用三段式级联**：文本/图案检测 → 水印先验打分 → 区块融合。人工确认卡在 LaMa 之前，检测永不直接触发修复。
2. **主检测器**：RapidOCR 3.10（PP-OCRv6 det small，ONNX Runtime CPU），只跑检测分支，`limit_type=max, limit_side_len=960`。本机实测 **0.18 s**，示例图 3 处水印文字全部命中，框贴合字形。
3. **遮罩按"区块"生成，不按"字形"生成**：det 框只覆盖目标区块面积的 51%，整块圆角矩形 + 外扩 0.25–0.35 倍行高 + 8–12 px 膨胀后到 80%（干净外溢仅 1–8%）。LaMa 对"多遮一点"不敏感，对"漏遮一条边"很敏感。
4. **再补两条几乎免费的通道**：FFT 自相关抓平铺水印（毫秒级，可反推每个 tile 的 alpha）、模板匹配抓固定 logo。学习式分割（自训 UNet + 合成数据，ONNX 5–20 MB）放第二阶段，专门补 logo、半透明底板这类字形之外的区域。
5. **明确不用**：VLM 出框（Florence-2 / Qwen2.5-VL）、GroundingDINO + SAM2、PaddleOCR 全家桶、SLBR 权重（无许可声明）、`demark`（GPL-3.0 传染）。

## 1. 问题拆解

"自动查找文字并划分遮罩区块"实际是四个子问题，混在一起谈就会得出"上一套大模型"这种错误结论：

| 子问题 | 真正的难点 | 可用信号 |
| --- | --- | --- |
| 找文字 | 半透明、低对比度、艺术字、中英混排 | 文本检测器（DBNet 系最稳） |
| 判断是水印 | 招牌、贴纸、衣服印花、海报标题也是文字 | 位置、重复次数、低饱和、透明度、字号 |
| 划区块 | 字形 ≠ 水印范围：描边、投影、半透明底板、logo 图形 | 框外扩、低梯度区域、版面先验 |
| 快速 | 用户不会为"定位"再等一个 3 s | 级联 + 降采样 + 结果缓存 |

关键判断：**文字检测的召回可以做到很高，但"这是水印"的判定做不到 100%**。实测一张干净的风景照，检测器也会把湖面的船认成一行字（§3）。因此产品形态只能是"给候选 + 一键确认"，不能是"自动删"。

## 2. 候选方案对比

| 方案 | 产出 | 中文/低对比度 | 速度（本机） | 体积/依赖 | 许可 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **PP-OCRv5/v6 det（RapidOCR + ORT CPU）** | 文本行四边形 | 强（3/3 命中半透明白字） | 0.18 s @960 | wheel 27.3 MB + ORT 16.7 MB | Apache-2.0 | ✅ **主选** |
| PaddleOCR 全流程（paddle 后端） | det + rec + cls | 强 | 同量级 | +paddlepaddle 数百 MB，Windows 轮子麻烦 | Apache-2.0 | ❌ 同模型改用 RapidOCR |
| CRAFT / EAST | 文本行 | 中 / 弱（低对比度差） | EAST 1 s+ | 40–90 MB | MIT / BSD | ❌ |
| Tesseract 5 | 词框 + 识别 | 弱（艺术字、水印易失败） | 0.3–1 s | 20 MB + 语言包 | Apache-2.0 | ❌ |
| Florence-2-large / Qwen2.5-VL（VLM 出框） | 语义框 / polygon | 中，能听懂"水印" | 1.5 GB + 2–5 s | transformers | MIT | ❌ 慢、框不稳、离线包大 |
| GroundingDINO + SAM2 | 文本 prompt → 框 → 精修 | 中，prompt 不稳 | 数百 MB + 0.5–2 s | torch 生态 | Apache-2.0 | ❌ 链路重；LaMa 不需要像素级轮廓 |
| SLBR / WDNet / WMFormer（端到端定位） | 水印 mask | 强（CLWD 训练） | 0.1–0.5 s（GPU） | 数百 MB | **未声明** | ❌ 许可不明，不能进 MIT 项目 |
| 自训 UNet / SegFormer-B0（合成数据） | 水印概率图 | 取决于数据，可覆盖 logo/底板 | 0.05–0.2 s | 5–20 MB ONNX | 自有 | ✅ **P2 主选** |
| FFT 自相关 + 模板匹配 | 平铺周期、tile 框、logo 框 | 极强（平铺场景） | 毫秒级 | 0（cv2/numpy） | 自有 | ✅ B 通道 |
| 形态学/阈值/alpha 反解 | 纯色字 mask、可无损还原 | 中（依赖先验） | <30 ms | 0 | 自有 | ✅ D 通道/兜底 |

速度列：PP-OCR 行为本机实测，其余为文献/经验估计（换硬件按比例缩放）。

被淘汰方案的共同问题不是"效果差"，而是**为了一个只占端到端 15% 的定位环节，引入 1 GB 级依赖或不确定的许可**。定位的正确投资回报在"融合与交互"，不在"换更大的模型"。

## 3. 实测：PP-OCR det 的实际表现

用 RapidOCR 3.10 只跑检测分支（`use_cls=False, use_rec=False`），在示例图与无文字原图上各测 5 次取中位数：

| 配置 | 耗时 | 框数 | GT 覆盖率 |
| --- | --- | --- | --- |
| 默认（限短边 736 / `min`） | 529 ms | 3 | 50.2% |
| `max` + 736 | 93 ms | 3 | 39.5%（框变小、漏边，别用） |
| **`max` + 960** | **177 ms** | **3** | **51.4%** |
| `max` + 1280 | 333 ms | 3 | 54.7% |
| 960 + `box_thresh .3 / thresh .2 / unclip 1.8` | 181 ms | 3 | 56.9% |
| 干净原图（无文字） | 173 ms | **1（误检）** | — |

![文字检测结果：绿框为 PP-OCRv6 det 在水印文字上的检出，logo 圆形标记与半透明底板不在框内](detect-probe.jpg)

同机重复测量波动约 ±10%，表内为 5 次中位数。

三个框正好对应示例图的三个水印文字元素：左上"© STOCK / LAMA"、右下"LAMA TRAVEL"与"旅行摄影 · 2026"。

由此得到三条直接可用的结论：

1. **降采样是最大的性能杠杆，但不能降太狠**。默认配置按原图长边推理（`limit_type=min` 对小图有利、对大图不利），显式设成 `max/960` 后耗时降到 1/3，框数与位置基本不变；再降到 736 虽然只要 93 ms，但框会缩水、GT 覆盖率掉到 39.5%，属于"快而不可用"。960 是拐点。
2. **字形 ≠ 区块**。3 个框的并集只覆盖 `demo-mask.png`（人工画的整块遮罩）面积的 **51%**。缺口来自：文字描边与投影、右下 logo 圆形标记、左上半透明深色底板（比文字宽 86 px）。按行高外扩后：

   | 外扩 | GT 覆盖 | 遮罩外溢 | 全图占比 |
   | --- | --- | --- | --- |
   | 0（贴合字形） | 51.4% | 0% | 1.43% |
   | 0.20 × 行高 | 70.1% | 1.2% | 1.97% |
   | 0.35 × 行高 | 80.3% | 7.9% | 2.42% |
   | 0.50 × 行高 | 84.8% | 18.7% | 2.89% |

   外溢的像素落在背景上，LaMa 重建得回来；漏掉的像素会在结果里留下"残影底板"。所以策略是**宁多勿少**：0.25–0.35 倍行高 + 8 px 膨胀起步。
3. **误检必须靠产品兜住**。干净风景图里那只船，score 0.63，形状像一行横排字。任何"自动删"的设计都会在这里翻车；换成 VLM 也一样（VLM 只会把幻觉换个位置）。

## 4. 推荐架构

```text
                     ┌──────── 预处理：长边 960–1280，可选白字/低对比度增强 ────────┐
 upload ── decode ───┤ EXIF、限 40 MB / 6000 万像素（复用现有 imaging.decode_image）│
                     └───────────────────────────┬──────────────────────────────┘
                                                 │
        ┌────────────────────────────────────────┼────────────────────────────────────────┐
  A 文本通道                                B 重复通道                              C 语义通道（P2）
  PP-OCRv6 det (ONNX, CPU)                  FFT 自相关 → 平铺周期                   自训 UNet / SegFormer
  → 文本行 quad + score                     + 模板匹配 → tile / logo 框             → 水印概率图
        └────────────────────────────────────────┼────────────────────────────────────────┘
                                                 │
                                  候选框融合：IoU/间距聚类、行合并、去重、最小尺寸
                                                 │
                                  水印先验打分（位置/重复/色调/均匀度）→ 高/中/低三档
                                                 │
                                  区块 blocks[]（rect + score + kind + 可选文本）
                                                 │
                        前端框选确认 ──► blocks_to_mask：圆角矩形 + 膨胀 + 羽化
                                                 │
                                  LaMa 修复（整图 or 逐块裁剪推理）
```

为什么是"通道并集"而不是"一个大模型"：

- 三个通道的失败模式几乎不重叠。文字通道漏掉的半透明底板、圆形 logo，正好是语义通道的强项；平铺水印对文字通道几乎不可见，对 FFT 是送分题。
- 每个通道都能独立回归测试，且最低配（A+B+D）零额外模型、零许可风险，一天能上线。
- C 通道晚一点上，不影响产品闭环。

## 5. 关键参数与算法

### 5.1 检测参数（A 通道）

```python
RapidOCR(params={
    "Det.limit_side_len": 960, "Det.limit_type": "max",   # 性能开关，实测 177 ms
    "Det.box_thresh": 0.3, "Det.thresh": 0.2,             # 抓低对比度水印，误检交给打分环节
    "Det.unclip_ratio": 1.8,                              # 框外扩，等价于半个遮罩膨胀
})
# 调用时只跑 det：ocr(img, use_det=True, use_cls=False, use_rec=False)
```

- 长边 > 2000 px 的图：要么把 det 的 `limit_side_len` 提到 1600（约 0.5 s），要么 2×2 分块检测（每块长边 960，重叠 10%）。否则原图里 12 px 的小字被压到 5 px 以下，直接漏检。
- `use_rec=True` 只在需要字符串先验时开（识别 "©"、"stock"、"小红书号" 一类命中表）。不要拿识别结果当"是水印"的证据——半透明水印的字形被背景混色，识别经常失败。

### 5.2 水印先验打分

```text
score = 0.45·det
      + 0.20·repeat      # 同图重复出现 / 命中 FFT 周期
      + 0.15·tone        # 低饱和高亮，或与局部背景色差小（半透明特征）
      + 0.10·position    # 距最近边 < 0.08·min(W,H)，或底部/右上角
      + 0.10·uniformity  # 块内笔画颜色、粗细一致（矢量叠加的水印更均匀）
```

分档：`≥0.65` 高置信（虚线框预显示，需点"应用"才生效）、`0.45–0.65` 中置信（提示"疑似水印"）、`<0.45` 不显示。权重是启发式，用 §9 的评测集回归，不要凭感觉调。

反例信号（命中直接降档）：框宽 > 0.3·W 且带透视/多色 → 场景文字；块内梯度方向杂乱 → 自然纹理被误判。

### 5.3 区块融合

1. **行合并**：水平间距 < 0.8 × 行高、垂直重叠 > 50% → 同一行。
2. **块合并**：行距 < 1.2 × 行高 → 同一块（"LAMA TRAVEL" 与 "旅行摄影 · 2026" 合成一个区块，避免 LaMa 两次推理交界）。
3. **去重**：IoU > 0.3 或包含关系只留分高的。
4. **剪枝**：面积 < 0.3% 画幅且高 < 12 px 的框丢弃；但若命中重复通道则保留。
5. 输出按 score 降序，编号稳定（同一张图多次检测编号不变，前端才能做"取消勾选"的记忆）。

### 5.4 遮罩生成

- 每块取 quad 的外接矩形，圆角 `r = min(8, 0.2·h)`，填充；
- 膨胀 `d = clamp(round(0.3·h), 8, 16)`（与现有 `dilate` 滑条叠加，别重复膨胀两次）；
- 羽化沿用现有合成阶段的 `feather`（2 px 起步）；
- 多个块用 `cv2.max` 合并，交集处不重复羽化。

**半透明底板/logo 的三种补法**（按成本递增）：

1. P0：固定比例外扩（上表 0.35 行高覆盖 80%），简单可靠；
2. P1：前端"框吸附"——拖框边时在 ±24 px 内找梯度最小的竖/横线对齐，让用户两秒收掉底板尾部；
3. P2：语义通道直接给底板/logo 的 mask，文字框只作为种子。

不要试图用纯规则从"文字框"推出"底板矩形"：底板可以比文字宽出近 90 px（示例图右侧就是这样），比例是任意的。

### 5.5 分块裁剪推理（可选优化，P1）

现状：3000 px 图缩到 1600–2048 推理，水印细笔画被抹平，结果放大回原尺寸后该区域偏软。分块后每块在原生细节上修复：

```text
for block in blocks:
    side = clamp(3 * max(block.w, block.h), 512, 1280)   # 四周各留 1 倍边长的上下文
    crop = centered_crop(image, block, side)
    pred = lama(crop, crop_mask)
    paste_back(crop, pred, feathered)                   # 只在遮罩区羽化
```

- 成本：1024² 一块约 0.4–0.8 s（4060），3 块仍 < 2 s；
- 风险：裁剪边缘过近会出现接缝或色差，需要"四周各留 ≥ 1/3 块边长"的约束；小块（<64 px）不要单独裁剪，直接并入整图推理；
- 收益：文字边缘更锐、未遮挡区域零像素改动。**这条需要在真机上验证再决定是否默认开启**。

### 5.6 alpha 反解（P3，平铺/纯色水印）

半透明统一水印满足 `I = (1-α)·B + α·W`。若从平铺块平均或直方图估出 `W`（水印色）与 `α`，可直接反解 `B = (I - α·W) / (1-α)`，比 LaMa 更保真且没有生成痕迹。适用纯色半透明字/logo；有投影、多色渐变、JPEG 块效应重的不适用。和 B 通道天然搭配：FFT 找到周期 → 平均出 W/α → 反解。

## 6. 性能预算

| 阶段 | 实测/估计 | 说明 |
| --- | --- | --- |
| 解码 1600×1067 | ~25 ms | 现有 `decode_image` |
| det @960 | **177 ms** | 实测，8C/16T |
| 融合 + 打分 | ~10 ms | numpy，几十个框 |
| mask 生成 + 膨胀 | ~10 ms | cv2 |
| **定位合计** | **~0.21 s** | 占端到端 < 15% |
| LaMa 推理 | 1–3.5 s | 不变 |
| 端到端 | ~1.3–4 s | 与现状同量级 |

- 笔记本 CPU（如 4060 游戏本）通常比 3700X 慢 1.3–1.8×，按 0.3–0.35 s 预算。
- 不建议上 `onnxruntime-gpu`：det 能降到 40–80 ms，但要多装 cuDNN 9（约 +300 MB）且与 torch 自带的 cuDNN 版本容易打架，为了 0.15 s 不值。
- 结果缓存：`sha256(image) → outputs/detect/<hash>.json`，48 小时随现有清理逻辑过期；同一张图反复调参数时不重复检测。

## 8. 交互与误检控制

- **默认不自动应用**：出框后停在"待确认"，用户点"应用全部"或逐框点选。高置信框用虚线预显示（不填色），避免制造"已经处理好了"的错觉。
- **三档可视化**：高置信虚线框 + 分数（应用前不填色），中置信虚线框 + "疑似"，低置信不显示（只在调试开关下可见）。
- **本地记忆**：用户取消过的框（位置比例 + 尺寸比例哈希）记在 `localStorage`，同图或同构图下次降权。
- **硬约束**：`/api/detect` 不允许触发 `/api/inpaint`；必须经过用户点击。这条写进代码注释，防止后续"自动化"改坏。
- **失败降级**：模型未加载 / 超时（>3 s）/ 无框 → 静默回落到手工涂抹，只在 toast 里说一句"未找到候选，请手动涂抹"。

## 9. 评测方法

- **评测集**：`samples/` 现有 2 张 + 合成 500 张（扩展 `make_demo.py`：字体、位置、透明度、底板、旋转、多行随机）+ 真实 100 张（文字水印 / logo / 平铺各 1/3）。
- **指标**：区块召回（IoU≥0.5 匹配到 GT 块）、GT 像素覆盖率、每图误检块数（FP/img）、p95 检测耗时、端到端耗时。
- **门槛**（先定死，再调参）：合成集 recall ≥ 0.95、FP/img ≤ 0.5；真实集以"确认后无残留、无误删"为准；p95 定位 ≤ 0.35 s（CPU）。
- **回归脚本**：`scripts/probe_detect.py`（本次实测用的探针，已入库），加 `--json` 输出结构化结果，可挂到 CI 或手动对比不同参数。

## 10. 落地路线

| 阶段 | 内容 | 工作量 | 验收 |
| --- | --- | --- | --- |
| **P0** | det-only + 阈值 + 三档打分（位置/色调）+ 前端框选确认 + `boxes` action | 0.5–1 人日 | 示例图 3/3 命中；干净图误检可一键取消；定位 < 0.35 s |
| **P1** | 行/块合并、外扩膨胀调参、检测缓存、框吸附、分块裁剪推理 | 1–2 人日 | 3000 px 图无接缝；遮罩覆盖率 ≥ 80% |
| **P2** | 合成数据自训 UNet/EffNet-B0 → ONNX；FFT 平铺通道 + 模板匹配 | 3–5 人日 | logo/底板场景 recall ≥ 0.9，模型 ≤ 20 MB |
| **P3** | alpha 反解、水印指纹库（同作者批量图复用）、批量模式 | 按需 | 纯色半透明水印可无损还原 |

## 11. 风险与许可

| 风险 | 应对 |
